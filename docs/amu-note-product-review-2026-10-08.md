# 아무노트 제품 비교 검토와 후속 작업 목록

## 문서 목적과 기준

사용자의 요청인 “만든 앱이 다른 앱에 비해 어떤 점이 부족한지 전반적으로 검토”한 결과를 다른 세션에서 항목별로 이어 처리할 수 있도록 기록한다.

- 검토일: 2026-10-08.
- 문서 작성일: 2026-10-09. 파일명은 원래 검토일을 기준으로 한다.
- 기준 커밋: `2ab5c01da478041e1d7b016b9ac8c37598555b22` (`main`).
- 환경: Windows, 로컬 Next.js 개발 서버 `http://localhost:3000`, 로그인 상태의 인앱 브라우저.
- 화면 확인: 보관함, 일반 문서 편집기, 설정, 390×844 크기의 일반 문서 화면.
- 코드 확인: 자동 저장, 목록 조회, 문서 서식 도구, Markdown 편집기, 그림판, 내보내기, 관련 제품 결정.
- 비교 대상: Notion, Apple 메모, OneNote, Obsidian의 공식 안내.
- 검토 당시 앱 코드는 변경하지 않았다. 발견한 문제의 후속 작업 파일만 추가했다.
- 기존 사용자 노트를 수정하거나 삭제하지 않았다. 좁은 화면 검토 후 브라우저 크기를 복원하고 검토용 탭을 닫았다.

**이 문서는 검토 결과와 개선 제안이다. 모든 기능 추가나 기존 제품 결정 변경이 승인됐다는 뜻은 아니다.** 사용자는 이 내용을 문서로 남겨 다른 세션에서 하나씩 처리하겠다고 요청했다. 확정된 범위는 [PRODUCT.md](../PRODUCT.md)와 [결정 색인](decisions/README.md)을 따른다. 기존 계약과 다른 기능을 구현할 때는 해당 항목의 범위를 먼저 정하고 계약을 갱신한다.

다음 세션에서는 기준 커밋 이후의 변경과 해당 후속 작업의 해결 여부를 확인한다. 이 문서의 과거 관찰을 최신 상태의 증거로 그대로 사용하지 않는다.

## 전체 판단

아무노트는 가볍게 기록하는 앱의 기본 구성을 갖췄다. 그러나 중요한 메모를 오래 쌓아 두는 주력 앱으로 쓰기에는 **저장 신뢰, 검색, 복구**가 부족하다. 기능 수를 늘리는 것보다 “쓰고 → 다시 찾고 → 실수해도 복구하는 흐름”을 먼저 완성하는 편이 효과가 크다.

현재의 장점은 다음과 같다.

- 일반 문서, Markdown, 그림판을 용도에 맞게 선택할 수 있다.
- 자동 저장, 동시 수정 충돌 감지, 휴지통과 복원 경로가 있다.
- 폴더와 정렬, 드래그 또는 창을 통한 이동이 있다.
- 읽기 전용 공유 링크를 켜고 끌 수 있다.
- 현재 편집 내용을 형식에 맞는 HTML, Markdown, SVG 파일로 내보낸다.
- 다국어 화면과 노트 배경 개인화를 지원한다.
- 개인 노트에 집중하고 있어 복잡한 협업 도구보다 단순한 경험을 유지할 여지가 있다.

다만 세 형식을 지원하는 폭에 비해 각 편집기의 수정·복구 기능이 얕고, 기록이 많아졌을 때 찾거나 다른 앱으로부터 가져오는 경로가 부족하다.

## 근거 구분과 검토의 한계

| 표기 | 의미 |
| --- | --- |
| 화면 확인 | 이번 검토에서 실제 화면 또는 DOM 측정으로 확인했다. |
| 코드 확인 | 구현 경로를 읽어 판단했다. 실제 사용 중 동일 결과를 재현한 것으로 보지 않는다. |
| 기존 기록 | 기존 후속 작업에 재현 또는 리뷰 근거가 있다. 이번에 새로 재현한 것은 아니다. |
| 개선 제안 | 사용성·경쟁력 관점의 제안이며 버그 판정이나 승인된 요구사항이 아니다. |

저장 직후 이탈에 따른 데이터 유실, 그림판 삭제 후 되돌리기, 색상 선택 상태는 이번에 사용자 노트를 수정해 재현하지 않았다. 모바일 검토는 브라우저 화면 크기를 바꾼 것으로, 실제 휴대폰의 키보드·터치·한글 조합 입력 검증을 대신하지 않는다. 운영 환경의 성능·부하, 전체 접근성, 보안·권한, 모든 언어·브라우저의 동작을 종합 검증한 결과도 아니다. 경쟁 앱은 공식 문서에 설명된 기능을 비교했으며 모든 앱을 직접 동일 조건으로 시험한 것은 아니다.

## 권장 처리 순서

1. **안심하고 쓰기:** 저장 대기·실패·충돌 표시, 초안 보존, 조회 오류 구분, 모바일 제목 영역, 그림판 되돌리기.
2. **쌓아도 찾기:** 제목·본문 통합 검색, 중요 노트 고정, 전체 노트 보기.
3. **오래 맡기기:** 수정 이력, 전체 백업·복원, 계정 복구 수단.
4. **작성과 정리의 편의:** 이미지·체크리스트·링크, 그림판 요소 편집, Markdown 보조, 빠른 기록, 일괄 정리, 긴 글 읽기.

아래 완료 기준은 다음 작업을 구체화하기 위한 제안이다. 구현 범위를 정할 때 필요한 것만 채택한다. 특히 오프라인 사용 전체, 계정 복구, 가져오기는 기존 결정 변경이 필요한 별도 주제다.

## 항목별 작업 목록

### R01. 저장 대기 상태와 화면 이탈 시 초안 보존

- [x] 재현 → 범위 확정 → 수정 → 검증 → 결과 기록.
- **처리 결과(2026-10-29):** 임시 일반 문서에서 입력 직후 새로고침하면 제목이 빈 값으로 돌아가는 문제를 재현했다. 입력 즉시 저장 대기를 표시하고 계정·노트별 브라우저 초안을 보관·복구한다. 정상 저장이 확인된 초안만 정리하며 저장 중 새 입력, 화면 재진입 뒤 도착하는 이전 응답, 서버 버전 충돌을 보호한다. 아래 과거 검토 근거는 당시 관찰로 남긴다.
- **문제:** 입력 후 저장 대기 중에도 `saved` 상태가 유지된다. 편집 화면이 unmount될 때 대기 타이머만 취소하는 구조여서 마지막 입력이 저장되지 않을 위험이 있다.
- **근거:** 코드 확인. [use-note-autosave.ts](../components/notes/use-note-autosave.ts)의 `scheduleSave`는 2초 대기 후 저장하고, 계속 입력하면 최대 30초 간격으로 저장한다. cleanup은 `clearTimers`다. 조사한 저장 경로에서 이탈 시 초안 보존은 확인되지 않았다.
- **영향:** 사용자는 “저장됨”을 보고 이동했는데 다시 열면 마지막 입력이 없을 수 있다. 실제 유실은 미재현이다.
- **첫 검증:** 임시 노트에서 정상 저장을 먼저 확인한 후 다른 내용을 입력하고 2초 이내 다른 노트로 이동, 새로고침, 탭 닫기를 각각 시험한다. 문서·Markdown·그림판·제목 변경에 공통 훅이 적용되는 점을 고려한다.
- **개선 방향:** 변경 즉시 미저장/저장 대기 표시, 초안 보존과 재진입 복구, 안전한 화면 전환을 함께 다룬다. 타이머 단축만으로 해결됐다고 보지 않는다.
- **완료 기준 제안:** 방금 입력한 내용의 저장 여부를 정확히 알 수 있고, 시험한 이탈 경로에서 미저장 내용이 복구 가능하다.
- **계약/검증:** [note-safety](decisions/note-safety.md), [브라우저 회귀 테스트](../e2e/autosave.spec.ts), [저장 훅 회귀 테스트](../components/notes/use-note-autosave.test.ts). 해결된 `autosave-pending-navigation` 후속 기록은 정리했다.

### R02. 저장 실패·충돌·연결 끊김 상태 구분

- [x] 현재 오류 경로 확인 → 표시와 복구 범위 확정 → 검증.
- **처리 결과(2026-10-29):** R01 이후 충돌이 저장 대기로 표시되던 상태를 `충돌 해결 대기`로 분리했다. 저장 실패·브라우저 연결 끊김에도 서버 저장 미확인과 기기 초안 보관 여부를 별도로 표시한다. 브라우저 연결 복구 뒤에는 버튼으로 재시도하고, 서버 응답이 성공했을 때만 저장 완료로 바꾼다. 연결 감지가 끊김이어도 사용자가 누른 재시도는 실제 요청으로 확인한다. 실제 요청 실패·연결 끊김·재시도와 R01 초안 복구 및 충돌 해결 8개 브라우저 흐름을 검증했다. 아래 문제와 근거는 초기 검토 당시의 기록이다.
- **문제:** 충돌 상태에서도 머리말이 “저장됨”으로 표시된다. 저장 함수는 반환된 `error`는 처리하지만 예외가 발생하는 경로에는 `finally`만 있어 네트워크 예외 시 표시와 재시도도 확인할 필요가 있다.
- **근거:** 충돌 표시는 기존 재현 기록과 코드 확인. 네트워크 예외의 실제 화면 결과는 미검증이다.
- **개선 방향:** 저장 대기, 저장 중, 저장 완료, 실패, 충돌 해결 대기를 구분한다. 서버에 저장된 상태와 이 기기에만 보존된 초안을 혼동시키지 않는다.
- **오프라인 비교:** 연결이 끊긴 동안 지속적으로 초안을 보관하고 재연결 후 이어 저장하는 경로가 부족하다. 완전한 오프라인 사용과 연결 실패 중 초안 보호는 범위를 나눠 정한다.
- **완료 기준 제안:** 충돌 중 저장 완료로 오해하지 않고, 실패해도 편집 내용이 남으며 재시도 결과를 확인할 수 있다.
- **계약/검증:** [note-safety](decisions/note-safety.md)는 기기 초안 보호와 상태 표시를 지원하고, 완전한 오프라인 사용과 자동 병합은 범위 밖으로 둔다. [상태·재시도 회귀 테스트](../e2e/save-status.spec.ts), [저장 훅 회귀 테스트](../components/notes/use-note-autosave.test.ts). 해결된 `conflict-banner-shows-saved` 후속 기록은 정리했다.

### R03. 조회 오류와 빈 보관함·없는 노트 구분

- [x] 실패 경로 재현 → 오류 전달과 재시도 화면 검증 → 결과 기록.
- **처리 결과(2026-10-29):** 개인 보관함·노트 본문·폴더·휴지통의 조회 실패를 정상 조회의 빈 결과와 구분하고, 실패 안내와 현재 주소에서 다시 시도하는 버튼을 제공한다. 없는 노트·다른 사용자의 노트·휴지통의 노트는 기존처럼 같은 404 경로를 사용한다. 서버 조회에 503 응답을 주입한 브라우저 검증으로 오류 표시, 실패가 계속될 때 재시도, 정상 응답으로 복구한 뒤 화면 복원을 확인했다. 아래 근거는 과거 검토 당시의 동작이다.
- **문제:** 조회 실패가 빈 목록 또는 404로 나타날 수 있다.
- **근거:** 기존 리뷰 기록과 [queries.ts](../lib/notes/queries.ts) 코드 확인. `listNotes`는 오류에서 `[]`, `getNote`는 `null`을 반환한다.
- **영향:** 일시적인 연결·서버 장애를 노트가 삭제된 것으로 오해한다.
- **완료 기준 제안:** 실제 빈 상태, 존재하지 않는 노트, 조회 실패를 구분하고 실패 시 다시 시도할 수 있다.
- **검증:** [조회 실패·재시도 회귀 테스트](../e2e/read-errors.spec.ts) 7개 흐름을 확인했다. `bun run test:e2e:reads`는 일반 개발 서버와 별도의 출력 디렉터리·3001 포트에서 서버 조회 실패를 주입한다. 해결된 `note-read-errors-look-like-empty` 후속 기록은 정리했다.

### R04. 제목·본문 통합 검색

- [ ] 검색 범위 결정 → 구현 → 여러 폴더의 임시 노트로 검증.
- **현재:** 보관함 화면은 폴더와 정렬 중심이며 제목·본문 통합 검색이 없다. 제품 정의에서도 내용 검색을 보류하고 있다.
- **영향:** 제목이나 보관 폴더가 기억나지 않고 본문 일부만 기억나는 메모를 찾기 어렵다.
- **개선 방향:** 제목·본문 검색과 일치 내용 미리보기부터 시작한다. 폴더 범위, 휴지통 포함 여부, 그림판 텍스트 포함 여부를 정한다. OCR은 첫 범위에 넣을 필요가 없다.
- **완료 기준 제안:** 다른 폴더에 있는 노트도 제목 또는 본문의 기억나는 문구로 찾아 열 수 있다.
- **근거/관련 코드:** 화면 확인, [PRODUCT.md](../PRODUCT.md), [library-shell.tsx](../components/notes/library-shell.tsx), [queries.ts](../lib/notes/queries.ts).
- **경쟁 비교:** Apple 메모와 OneNote는 본문 검색을 제공하며 일부 환경에서는 필기·이미지 속 글자도 검색한다. 출처 S1, S2.

### R05. 중요 노트 고정·전체 노트 보기·태그

- [ ] 고정과 전체 보기 범위 결정 → 구현·검증. 태그는 별도 필요성 판단.
- **현재:** 폴더별 목록과 정렬은 있지만 고정, 태그, 폴더를 가로지르는 전체 노트 탐색이 부족하다.
- **개선 방향:** 자주 쓰는 노트 고정과 전체 노트 보기를 먼저 검토한다. 태그·스마트 폴더는 검색과 고정으로 부족한 경우에 이어 판단한다.
- **완료 기준 제안:** 자주 보는 노트를 매번 폴더 탐색 없이 열 수 있고, 전체 보기의 노트에서 원래 폴더 위치를 알 수 있다.
- **관련 코드:** [library-shell.tsx](../components/notes/library-shell.tsx), [queries.ts](../lib/notes/queries.ts).
- **경쟁 비교:** Apple 메모는 고정, 태그, 스마트 폴더를 제공한다. 출처 S3.

### R06. 수정 이력과 이전 버전 복원

- [ ] 보관 단위·기간·복원 방식 결정 → 임시 노트로 검증.
- **현재:** 휴지통은 있지만 본문을 잘못 수정한 뒤 저장했을 때 이전 버전으로 되돌리는 사용자 기능은 없다. 충돌 감지용 버전 번호를 복원 가능한 이력과 혼동하지 않는다.
- **개선 방향:** 최근 버전 보기와 복원 경로를 설계한다. 저장 주기와 보관량, 제목·본문·그림의 복원 범위, 복원 전 현재 내용 보존을 정한다.
- **완료 기준 제안:** 잘못 덮어쓴 임시 노트를 이전 상태로 복원할 수 있고, 복원 때문에 최신 내용이 조용히 사라지지 않는다.
- **계약:** [note-safety](decisions/note-safety.md).
- **경쟁 비교:** Notion은 요금제별 이력을 제공하며 검토 시점 공식 문서상 무료 플랜은 7일이다. 출처 S4.

### R07. 계정 복구와 계정 관리

- [ ] 기존 정책 재검토 → 복구 수단 결정 → 별도 범위로 구현·검증.
- **현재:** 자체 아이디·비밀번호 계정은 비밀번호를 잊으면 복구할 수 없도록 설계됐다. 설정은 계정 표시·로그아웃·언어·기본 배경·앱 정보 중심이다.
- **근거:** 설정 화면 확인과 [account-identity](decisions/account-identity.md) 계약.
- **영향:** 중요한 메모를 맡기려는 사용자에게 계정 접근 상실의 부담이 크다.
- **개선 방향:** 선택형 복구 이메일 등 가능한 수단과 가입 단순성의 대가를 판단한다. 계정 관리의 추가 필요도 함께 살피되, 이번 비교만으로 특정 인증 방식을 채택하지 않는다.
- **완료 기준 제안:** 채택한 계정 유형에서 사용자가 안내된 절차로 접근을 복구할 수 있다. 외부 로그인 계정과 자체 계정의 경로를 구분한다.
- **주의:** 의도된 정책의 변경이다. 로그인·DB 관련 작업 전 해당 프로젝트의 Supabase 스킬과 지침을 따른다.

### R08. 전체 백업·복원과 다른 앱에서 가져오기

- [ ] 백업과 가져오기 범위를 구분해 결정 → 파일 예제로 검증.
- **현재:** 개별 일반 문서는 HTML, Markdown은 `.md`, 그림판은 SVG로 내보낸다. 전체 백업과 다시 가져오기는 없다. 내보내기는 현재 편집 내용을 사용한다.
- **영향:** 노트가 많으면 하나씩 반출해야 하고, 파일을 받아도 폴더와 편집 가능한 앱 상태를 복원할 수 없다. 다른 앱에서 쌓아 둔 메모를 옮겨 오는 비용도 크다.
- **개선 방향:** 전체 백업·복원과 외부 형식 가져오기는 별도 작업으로 나눈다. 외부 가져오기는 Markdown·HTML부터 검토한다. 폴더, 배경, 첨부, 충돌·중복 이름의 처리 범위를 정한다.
- **완료 기준 제안:** 선택한 범위의 임시 노트를 반출·복원한 뒤 내용과 구조가 유지된다. 외부 형식에서 보존하지 않는 정보는 사용자가 알 수 있다.
- **계약/코드:** [note-sharing](decisions/note-sharing.md)은 가져오기를 제외하고 있다. [export.ts](../lib/notes/export.ts).
- **경쟁 비교:** Obsidian은 공식 Importer와 로컬 파일 보관 경로를 제공한다. 출처 S6.

### R09. 모바일 제목과 도구 배치, 긴 본문 가로 넘침

- [ ] 좁은 화면 재현 → 배치 수정 → 실기기 또는 키보드 포함 검증.
- **화면 확인:** 390×844 일반 문서 화면에서 `Note title` 입력 폭이 약 14px, 서식 도구 높이가 약 141px였다. 현재 문서는 본문 `clientWidth` 311px, `scrollWidth` 552px로 가로 스크롤이 생겼다.
- **영향:** 제목이 거의 보이지 않고 작성·읽기 공간이 줄어든다.
- **개선 방향:** 제목을 별도 줄에 배치하고 부가 작업을 더보기로 묶는 방안을 검토한다. 하단은 자주 쓰는 서식을 우선 노출한다. 긴 코드·URL·기존 붙여넣기 내용의 넘침을 별도로 확인한다.
- **완료 기준 제안:** 좁은 화면에서 제목을 읽고 편집할 수 있고 주요 작업에 접근 가능하다. 본문 전체의 불필요한 가로 스크롤을 줄이되 코드 등 필요한 가로 스크롤은 구분한다. 키보드가 열린 상태도 확인한다.
- **한계:** 측정한 특정 기존 문서의 결과다. 모든 문서가 같은 폭으로 넘친다는 뜻은 아니다. 실제 터치·키보드·한글 입력은 미검증이다.
- **관련 코드/기록:** [note-frame.tsx](../components/notes/note-frame.tsx), [format-bar.tsx](../components/notes/format-bar.tsx), [모바일 후속 작업](follow-ups/mobile-note-title-collapses.md).

### R10. 일반 문서의 이미지·체크리스트·링크·표

- [ ] 필요한 콘텐츠 유형부터 범위 결정 → 편집·저장·공유·내보내기 검증.
- **현재:** 글꼴·크기·색상·강조·목록·정렬 등은 지원하지만 본문 이미지, 표, 체크리스트, 링크 편집 도구가 부족하다. Markdown으로 표현 가능한 기능과 일반 문서 도구를 구분한다.
- **영향:** 회의록, 공부 자료, 업무 스크린샷을 한 노트에 모으기 어렵다.
- **개선 방향:** 이미지 붙여넣기, 체크리스트, 링크부터 검토하고 표는 사용 필요에 맞춰 추가한다. 저장된 본문뿐 아니라 공유와 내보내기에서의 표현도 정한다.
- **완료 기준 제안:** 채택한 콘텐츠를 넣고 다시 열어 수정할 수 있으며, 공유·내보내기에서 약속한 표현이 유지된다.
- **계약:** [note-formats](decisions/note-formats.md)은 일반 문서의 표·이미지·링크를 명시적으로 제외한다. 범위 변경 전 계약 재검토가 필요하다.
- **경쟁 비교:** Apple 메모는 표, 체크리스트, 첨부, 노트 간 링크를 제공한다. 출처 S3.

### R11. 색상 도구가 가리키는 상태의 일관성

- [ ] 다른 색의 임시 텍스트로 선택 상태 재현 → 표시 의미 결정 → 검증.
- **문제:** `ColorButton`은 `initialColor`에서 시작한 자체 상태를 표시한다. 선택한 글의 실제 색이 달라도 띠와 입력 값이 따라오지 않는 구조다.
- **근거:** [format-bar.tsx](../components/notes/format-bar.tsx) 코드 확인. 화면에서 선택을 바꿔 재현하지는 않았다.
- **개선 방향:** 현재 선택한 글의 색, 여러 색이 섞인 선택, 최근 사용 색을 구분한다. 최근 색을 표시하는 방식 자체가 잘못은 아니지만 UI가 무엇을 뜻하는지 일관돼야 한다.
- **완료 기준 제안:** 서로 다른 색의 글자를 선택했을 때 도구가 약속한 의미대로 표시되며, 다시 열어도 오해를 일으키지 않는다.
- **계약/기록:** [note-formats](decisions/note-formats.md)의 선택 서식 되읽기 계약, [색상 후속 작업](follow-ups/color-controls-ignore-selection.md).

### R12. 그림판 삭제 후 되돌리기와 다시 실행

- [ ] 임시 그림판에서 추가·삭제·되돌리기 재현 → 작업 이력 범위 결정 → 검증.
- **문제:** `erase`는 요소를 삭제하고 `undo`는 남은 배열의 마지막 요소만 제거한다. 지운 요소를 복원하지 못하고 다른 요소를 추가로 지우는 구조다. 다시 실행도 부족하다.
- **근거:** [canvas-editor.tsx](../components/notes/canvas-editor.tsx) 코드 확인. 화면 재현은 미실시다.
- **첫 검증:** 요소 A·B를 추가하고 A를 지운 후 되돌리기를 눌러 결과를 확인한다. 사용자 원본 그림을 시험에 사용하지 않는다.
- **개선 방향:** 추가·삭제를 포함한 작업 이력과 다시 실행을 검토한다. 기존 “요소 하나씩 되돌리기” 계약과 사용자 기대의 차이를 정리한다.
- **완료 기준 제안:** 지우기 직전 상태를 복원할 수 있고, 반복 되돌리기·다시 실행이 정해진 규칙대로 동작한다.
- **기록:** [그림판 후속 작업](follow-ups/canvas-undo-after-erase.md).

### R13. 그림판의 기존 요소 편집

- [ ] 선택·이동·크기 변경·텍스트 수정 중 범위 선택 → 검증.
- **현재:** 추가 중심이며 기존 요소를 선택해 위치·크기·텍스트를 고치는 기능이 부족하다. 그림면은 620×400 고정 크기다.
- **영향:** 간단한 스케치를 고치려 해도 지우고 다시 만들어야 한다.
- **개선 방향:** 요소 선택과 이동, 도형 크기 변경, 기존 텍스트 재편집을 순차 검토한다. R12의 작업 이력과 함께 설계하면 편집 취소 규칙을 유지하기 쉽다.
- **완료 기준 제안:** 만든 요소를 수정하고 다시 열었을 때 결과가 유지된다.
- **계약/코드:** [note-formats](decisions/note-formats.md), [canvas-editor.tsx](../components/notes/canvas-editor.tsx), [canvas.ts](../lib/notes/canvas.ts). 무한 캔버스와 확대·축소는 현재 범위 밖이며 자동으로 추가하지 않는다.

### R14. Markdown 작성 보조

- [ ] 반복적으로 불편한 입력을 선정 → 작은 보조 기능부터 검증.
- **현재:** 원문 입력과 미리보기 중심이다. 목록 이어쓰기, 링크·이미지 입력 같은 작성 보조가 부족하다.
- **개선 방향:** 목록 입력 보조와 링크·이미지 삽입 편의를 검토한다. 미리보기에서 표현되는 것과 원문 편집 도구의 유무를 구분한다.
- **완료 기준 제안:** 선택한 작성 흐름이 원문을 뜻하지 않게 바꾸지 않으면서 더 적은 조작으로 완료된다.
- **관련 코드:** [markdown-editor.tsx](../components/notes/markdown-editor.tsx).

### R15. 글과 그림을 함께 활용하는 경로

- [ ] 실제 사용 예로 연결 방식 결정 → 원본 보존 검증.
- **현재:** 노트마다 형식을 선택하고 만든 뒤 바꾸지 않는다. 한 노트에서 글과 그림을 함께 활용하는 데 제약이 있다.
- **개선 방향:** 형식을 통째로 변환하기보다 그림·이미지를 문서에 넣는 연결부터 검토한다. R10과 연결되지만 모든 형식을 하나의 편집기로 합친다는 뜻은 아니다.
- **완료 기준 제안:** 합의한 경로로 그림을 문서에서 활용할 수 있고 원본 노트가 손상되지 않는다.
- **계약:** [note-formats](decisions/note-formats.md)은 형식 변환과 형식 통합을 현재 채택하지 않는다.

### R16. 빠른 기록 진입

- [ ] 현재 생성 흐름 측정 → 바로 만들기 방식 결정 → 키보드·마우스 검증.
- **현재:** 앱을 열고 새 노트의 형식을 골라 기록하는 흐름이다.
- **개선 방향:** 최근 사용 형식으로 바로 만들기, 새 노트 단축키를 검토한다. 형식 선택권은 유지한다.
- **완료 기준 제안:** 반복 사용자가 자주 쓰는 형식의 빈 노트를 빠르게 열고 바로 입력할 수 있다. 기존 입력 단축키와 충돌하지 않는다.

### R17. 여러 노트의 일괄 정리

- [ ] 여러 노트 선택·이동 범위 결정 → 폴더 구조와 함께 검증.
- **현재:** 정리 흐름이 개별 노트 중심이다.
- **개선 방향:** 여러 노트의 일괄 이동부터 검토한다. 일괄 삭제 등 영향이 큰 동작을 자동으로 같은 범위에 넣지 않는다.
- **완료 기준 제안:** 선택한 노트만 대상 폴더로 이동하고 선택하지 않은 노트는 그대로 남는다.

### R18. 공유·전달과 인쇄·PDF

- [ ] 실제 전달 수요 확인 → 인쇄 또는 PDF 범위 결정 → 결과 확인.
- **현재:** 읽기 전용 공유 링크와 형식별 파일 반출이 있다. 댓글·공동 편집, 공유 링크 비밀번호·만료는 기존 범위 밖이다.
- **개선 방향:** 받는 사람이 보기 쉬운 인쇄·PDF 수요를 먼저 확인한다. HTML·Markdown·SVG 원본 내보내기를 없애는 방식으로 바꾸지 않는다.
- **완료 기준 제안:** 합의한 방식으로 긴 글과 그림을 잘림 없이 전달할 수 있다. 배경 포함 여부와 페이지 나눔을 명시한다.
- **계약/코드:** [note-sharing](decisions/note-sharing.md), [export.ts](../lib/notes/export.ts).

### R19. 긴 글 읽기와 문서 안 탐색

- [ ] 긴 업무 메모의 불편 확인 → 제목·목차·접기 중 범위 선택.
- **현재:** 긴 글의 목차, 제목 단위 접기 등 탐색 기능이 부족하다.
- **개선 방향:** 장문 사용이 잦다면 제목 구조와 목차, 섹션 접기를 검토한다. 전체 노트 검색(R04)과 한 문서 안의 탐색은 별개다.
- **완료 기준 제안:** 긴 문서에서 원하는 부분을 반복 스크롤 없이 찾아갈 수 있다.

### R20. 무료 운영의 지속성과 사용자 안내

- [ ] 저장 용량·백업·반출 방침의 현재 상태 확인 → 필요한 정책 결정.
- **현재:** 제품은 무료·광고 없음 방향이지만 무료 운영의 지속 방식은 [PRODUCT.md](../PRODUCT.md)에 미정으로 남아 있다.
- **영향:** 장기 사용자에게 자료를 얼마나 오래, 어떤 조건으로 맡길 수 있는지 설명하기 어렵다.
- **개선 방향:** 저장 용량, 백업, 장애 대응, 서비스 종료 시 반출 방침을 먼저 정리한다. 이 검토가 유료화나 특정 수익 모델을 결정한 것은 아니다.
- **완료 기준 제안:** 실제 운영 가능한 약속과 사용자 안내가 일치한다.

## 당장 우선하지 않을 기능과 별도 판단할 경계

AI 요약, 실시간 공동 편집, 복잡한 데이터베이스 기능을 먼저 추가할 필요는 없다는 것이 이번 검토의 권고다. 개인 노트의 단순함을 유지하면서 저장·탐색·복구를 완성하는 편을 추천했다. 이 권고는 해당 기능을 영구히 금지하는 새 결정이 아니다.

검색, 가져오기, 복구 수단, 오프라인, 본문 첨부, 형식 간 연결에는 기존에 보류하거나 제외한 범위가 섞여 있다. 부재 자체를 전부 버그로 취급하지 않는다. 우선 한 작업만 골라 해당 제품 결정을 확인하고 범위를 정한다.

## 다음 세션의 시작 절차

1. 현재 `git status`와 커밋을 확인하고 이 문서의 기준 이후에 이미 해결된 항목이 있는지 확인한다.
2. R01부터 또는 사용자가 지정한 항목 하나를 선택한다. 관련 결정 계약과 후속 작업을 읽는다.
3. 근거가 코드 확인에 그친 항목은 임시 데이터로 먼저 재현한다. 사용자 원본 메모를 덮어쓰거나 공유·삭제하지 않는다.
4. 기존 결정 변경이 필요한 경우 선택한 작업의 범위를 정한 후 계약을 갱신한다. 이 문서를 일괄 구현 승인으로 사용하지 않는다.
5. 변경에 필요한 프로젝트 지침과 스킬을 적용한다. Next.js 코드를 쓸 때 설치된 버전 문서를 읽고, Supabase 작업은 해당 공식 스킬과 지침을 따른다.
6. 현재 AGENTS.md의 검증·리뷰 예산을 따른다. 자동 리뷰는 최대 1회 낮은 강도로 수행하며, 리뷰어를 부를 수 없으면 그 사실을 남긴다. 주 경로와 합의한 완료 기준을 중심으로 검증한다.
7. 아래 기록에 구현 범위, 확인한 결과, 남은 한계와 커밋을 적고 해당 항목의 체크박스를 갱신한다. 제안된 기능을 보류하기로 했으면 구현 완료와 구분해 기록한다.
