# 계정 식별자

## Decisions

- 자체 계정은 아이디와 비밀번호로만 만든다. 이메일과 전화번호는 받지 않는다.
- 아이디는 계정을 가리키는 공개 식별자이며 유일하다. 가입 화면에서 중복 여부를 미리 확인할 수 있어야 한다.
- Supabase Auth에는 아이디에서 만든 내부 전용 이메일로 계정을 등록한다. 이 값은 사용자에게 보여주지 않고, 사용자가 입력하지도 않으며, 메일을 보내는 데 쓰지 않는다.
- 비밀번호 해싱과 세션은 Supabase Auth의 기본 경로를 그대로 쓴다. 직접 구현하지 않는다.
- 비밀번호 재설정과 계정 복구 경로는 두지 않는다. 비밀번호를 잊으면 그 계정과 그 안의 노트에 다시 접근할 수 없다. 가입 화면은 이 사실을 사용자에게 미리 알린다.

## Boundaries

- 외부 로그인 공급자는 이 계약의 범위가 아니다. Google, GitHub, GitLab 같은 OAuth 계정은 공급자가 주는 식별자를 그대로 쓴다.
- 내부 전용 이메일의 구체적인 형태는 이 계약이 정하지 않는다. 사용자에게 노출되지 않고 실제 메일 주소와 충돌하지 않으면 된다.
- "이메일을 받지 않는다"는 자체 계정 가입에 대한 것이다. 나중에 복구용 이메일을 선택 항목으로 더하는 일까지 막지는 않는다.

## Why

Supabase Auth의 비밀번호 인증은 식별자로 이메일과 전화번호만 지원한다. 아이디로 로그인하려면 어느 쪽이든 우회가 필요하다.

비밀번호 해싱과 세션 관리를 직접 만드는 것이 가장 큰 위험이므로, 그 부분은 Supabase의 검증된 경로에 그대로 남기고 식별자만 우리 쪽에서 아이디로 바꾼다. 내부 전용 이메일은 그 목적 하나를 위한 값이다.

대가는 복구 경로가 없다는 것이다. 이메일이 없으면 본인 확인 수단이 없기 때문이다. 이 앱은 개인 저장소이므로 계정을 잃으면 노트도 잃는다. 가입 화면에서 이를 미리 알리는 것이 이 결정의 일부다.

## Reconsider when

- Supabase Auth가 username을 1급 식별자로 지원할 때. 그때는 내부 전용 이메일 우회를 걷어낸다.
- 비밀번호 분실로 계정을 잃었다는 신고가 반복될 때. 복구용 이메일을 선택 항목으로 더할지 다시 판단한다.

## Still-rejected alternatives

- 이메일과 비밀번호로 가입받기 — Supabase 기본 경로라 가장 단순하지만, 아이디 중복 확인 화면이 사라지고 사용자가 쓰기로 한 로그인 방식과 달라진다. Supabase가 username을 지원하면 이 비교 자체가 사라진다.
- 아이디와 이메일을 함께 받기 — 복구 경로가 생기지만 "아이디와 비밀번호로만 단순하게"라는 요구와 어긋나고 가입 입력이 늘어난다. 복구 요구가 실제로 커지면 다시 본다.
- 비밀번호 인증을 직접 구현하기 — 해싱, 세션, 토큰 갱신을 모두 떠안게 되고 얻는 것은 식별자 자유뿐이다.

## Evidence worth preserving

- Supabase 공식 문서 [Password-based Auth](https://supabase.com/docs/guides/auth/passwords)는 비밀번호 인증의 식별자로 이메일과 전화번호만 다룬다. username은 없다.
- [Password Security](https://supabase.com/docs/guides/auth/password-security)에 따르면 최소 길이와 문자 종류 요구는 프로젝트 Auth 설정에서 강제할 수 있다. 유출 비밀번호 차단(HaveIBeenPwned)은 Pro 플랜 이상이라 무료 운영과 맞지 않는다.
