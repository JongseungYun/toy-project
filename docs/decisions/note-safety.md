# 노트를 잃지 않는 규칙

## Decisions

- 사용자가 저장을 누르지 않아도 편집 내용이 보관된다. 저장 중인지, 저장됐는지, 실패했는지가 화면에 보인다. 실패해도 쓰던 내용을 잃지 않는다.
- 다른 기기가 같은 노트를 먼저 바꿔 두었으면 조용히 덮지 않는다. 충돌을 알리고 사용자가 내 내용으로 덮을지 최신 내용을 불러올지 고른다. 고르기 전에는 어느 쪽도 사라지지 않는다.
- 모든 삭제는 휴지통을 거친다. 되돌릴 수 없는 삭제를 기본 동작으로 두지 않는다.
- 폴더를 지우면 그 안의 하위 폴더와 노트가 함께 휴지통으로 가고, 되돌리면 원래 있던 자리로 돌아간다.
- 영구 삭제는 사용자에게 확인받은 뒤에만 이루어진다.
- 휴지통을 자동으로 비우는 보관 기간은 두지 않는다. 사용자가 비우기 전까지 그대로 쌓인다.
- 한 사용자의 노트, 폴더, 배경 이미지는 그 사용자만 읽고 쓸 수 있다. 화면에서 거르는 것이 아니라 데이터베이스가 막는다.

## Boundaries

- 충돌 처리는 실시간 공동 편집의 대체물이 아니다. 한 사람이 여러 기기를 쓰는 상황을 위한 것이다.
- 자동 저장의 간격(입력이 멈추고 약 2초, 계속 쓰는 중이면 최대 30초)은 값이 싼 선택이다. 더 나은 근거가 나오면 바꿔도 된다. 바꾸면 안 되는 것은 "사용자가 저장을 의식하지 않는다"는 쪽이다.
- 연결이 끊긴 동안의 편집 보관과 재접속 병합은 범위 밖이다.

## Why

제품이 "저장을 신경 쓰지 않아도 안전하게 보관된다"를 약속한다. 그 약속을 깨는 방법은 두 가지다. 사용자가 쓴 것을 조용히 덮거나, 되돌릴 수 없게 지우는 것이다.

마지막 저장이 이기는 방식은 다른 기기에서 쓴 내용을 예고 없이 지운다. 실시간 공동 편집이 범위 밖이라 병합할 방법도 없으므로, 알리고 고르게 하는 것이 내용을 지키는 가장 단순한 길이다.

폴더는 깊이 제한 없이 중첩된다. 폴더 하나를 잘못 지르면 그 아래가 통째로 사라지므로, 즉시 삭제를 기본으로 둘 수 없다.

소유자 격리를 데이터베이스에 두는 이유는, 화면을 건너뛰고 API를 직접 부르는 요청이 언제나 가능하기 때문이다. 조건을 코드에 두면 한 곳만 빠뜨려도 새어 나간다.

## Reconsider when

- 휴지통이 쌓여 저장 용량이 문제가 될 때. 자동 비우기를 두더라도 기간을 사용자에게 먼저 알리고 고르게 하는 쪽을 본다.
- 오프라인 편집 요구가 생길 때. 그때는 충돌 처리의 전제(내가 불러온 뒤 다른 기기가 바꿨는가)부터 다시 본다.

## Still-rejected alternatives

- 마지막 저장이 이기게 두기 — 구현이 가장 단순하지만 한 사람이 두 기기를 쓰는 흔한 상황에서 내용이 사라진다.
- 삭제 확인 창만 두고 즉시 지우기 — 휴지통보다 단순하지만, 폴더를 잘못 지웠을 때 되돌릴 방법이 없다.
- 소유자 조건을 애플리케이션 쿼리에만 두기 — 빠르지만 한 경로만 빠뜨려도 남의 노트가 새어 나간다.
