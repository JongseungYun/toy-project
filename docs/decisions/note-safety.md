# 노트를 잃지 않는 규칙

## Decisions

- 사용자가 저장을 누르지 않아도 편집 내용이 보관된다. 저장 중인지, 저장됐는지, 실패했는지가 화면에 보인다. 실패해도 쓰던 내용을 잃지 않는다.
- 입력 즉시 저장 대기를 표시하고, 제목과 본문의 미저장 초안을 현재 브라우저에 계정·노트별로 보관한다. 이동·새로고침·탭 닫기 후 같은 노트를 열면 복구해 저장을 이어가며, 서버 저장이 확인된 초안만 정리한다. 복구 중 서버 버전이 달라졌으면 기존 충돌 선택을 거친다.
- 저장 대기·저장 중·서버 저장 완료·실패·연결 끊김·충돌 해결 대기를 구분한다. 실패·연결 끊김·충돌 상태에는 브라우저 초안의 보관 여부도 함께 표시한다. 연결이 돌아온 뒤에는 사용자가 재시도해 저장하며, 연결됐다는 이유만으로 저장 완료로 표시하지 않는다.
- 다른 기기가 같은 노트를 먼저 바꿔 두었으면 조용히 덮지 않는다. 충돌을 알리고 사용자가 내 내용으로 덮을지 최신 내용을 불러올지 고른다. 고르기 전에는 어느 쪽도 사라지지 않는다.
- 제목·본문은 서버의 수정 이력으로 되살릴 수 있다. 약 5분 간격으로 묶은 최근 50개 복원 지점을 기간 제한 없이 보관한다. 첫 편집 전과 복원 직전 상태는 간격과 관계없이 남기며, 50개를 넘으면 오래된 지점부터 정리한다. 변경이 없거나 정리 설정만 바뀐 저장은 본문 이력을 늘리지 않는다.
- 복원은 현재 내용의 저장을 확인한 뒤 선택한 내용을 새 편집 버전으로 적용한다. 직전 내용도 이력에 남기며 다른 기기의 수정과 미저장 초안을 조용히 덮지 않는다. 폴더·고정·노트 배경·공유 설정과 형식은 유지한다. 이력은 소유자만 읽고 복원하며, 휴지통 복원 시 유지되고 노트를 영구 삭제하면 함께 삭제된다.
- 모든 삭제는 휴지통을 거친다. 되돌릴 수 없는 삭제를 기본 동작으로 두지 않는다.
- 폴더를 지우면 그 안의 하위 폴더와 노트가 함께 휴지통으로 가고, 되돌리면 원래 있던 자리로 돌아간다.
- 돌아갈 자리가 아직 휴지통에 있으면 보관함 뿌리로 올려 보이게 한다. 되돌린 것이 어디에도 보이지 않는 상태로 남지 않는다.
- 영구 삭제는 사용자에게 확인받은 뒤에만 이루어진다.
- 휴지통을 자동으로 비우는 보관 기간은 두지 않는다. 사용자가 비우기 전까지 그대로 쌓인다.
- 한 사용자의 노트, 폴더, 배경 이미지는 그 사용자만 읽고 쓸 수 있다. 화면에서 거르는 것이 아니라 데이터베이스가 막는다.
- 이 규칙을 여는 것은 사용자가 직접 켠 공유 링크 하나뿐이다. 그때도 열리는 것은 열쇠가 가리키는 노트 하나의 읽기이고, 여는 자리도 표가 아니라 열쇠를 받는 함수다. [note-sharing](note-sharing.md) 참고.

## Boundaries

- 충돌 처리는 실시간 공동 편집의 대체물이 아니다. 한 사람이 여러 기기를 쓰는 상황을 위한 것이다.
- 자동 저장의 간격(입력이 멈추고 약 2초, 계속 쓰는 중이면 최대 30초)은 값이 싼 선택이다. 더 나은 근거가 나오면 바꿔도 된다. 바꾸면 안 되는 것은 "사용자가 저장을 의식하지 않는다"는 쪽이다.
- 이동과 새로고침에 대비한 브라우저 초안 보호는 지원한다. 오프라인에서 보관함을 열어 쓰는 기능과 재접속 시 자동 병합은 범위 밖이다. 브라우저 저장소가 차단되거나 가득 찼으면 임시 보관 실패를 표시한다.
- 수정 이력은 기능 적용 이후의 복원 지점만 제공하며, 적용 전에 사라진 내용을 재구성하지 않는다. 글자 단위 비교·자동 병합·정리 설정의 이력 복원은 범위 밖이다.

## Why

제품이 "저장을 신경 쓰지 않아도 안전하게 보관된다"를 약속한다. 그 약속을 깨는 방법은 두 가지다. 사용자가 쓴 것을 조용히 덮거나, 되돌릴 수 없게 지우는 것이다.

저장 대기 중 화면을 떠나면 서버 요청이 시작되기 전일 수 있고, 탭을 닫을 때 보내는 요청의 완료도 보장할 수 없다. 그래서 입력 순간 브라우저에 초안을 남기고 서버 응답을 확인한 뒤 정리한다. 복구할 초안의 기준 버전을 함께 보관해야 다른 기기의 최신 내용을 조용히 덮지 않는다.

마지막 저장이 이기는 방식은 다른 기기에서 쓴 내용을 예고 없이 지운다. 실시간 공동 편집이 범위 밖이라 병합할 방법도 없으므로, 알리고 고르게 하는 것이 내용을 지키는 가장 단순한 길이다.

현재 노트가 안전하게 저장됐어도 실수한 수정이 함께 저장될 수 있다. 복원 지점을 별도로 보관하고 복원 직전 상태도 남기면 그 작업을 다시 되돌릴 수 있다. 개수로 보관량을 제한하되 날짜로 지우지 않으면 자주 고치지 않는 노트의 이력이 시간만 지나 사라지는 일을 피한다.

폴더는 깊이 제한 없이 중첩된다. 폴더 하나를 잘못 지르면 그 아래가 통째로 사라지므로, 즉시 삭제를 기본으로 둘 수 없다.

되돌린 것을 원래 자리에 두는 것보다 보이게 하는 것이 먼저다. 하위 폴더를 먼저 지우고 상위 폴더를 나중에 지우면 되돌릴 자리가 휴지통에 남아 있을 수 있는데, 그때 원래 자리를 고집하면 되돌린 폴더가 보관함에도 휴지통에도 나타나지 않는다. 사용자는 되살렸다고 생각하지만 화면에서는 사라진 것과 구별되지 않는다.

소유자 격리를 데이터베이스에 두는 이유는, 화면을 건너뛰고 API를 직접 부르는 요청이 언제나 가능하기 때문이다. 조건을 코드에 두면 한 곳만 빠뜨려도 새어 나간다.

공유도 같은 자리에서 연다. 화면이 "이 노트는 공유 중이니 보여 주자"라고 판단하면, 화면을 거치지 않는 요청이 그 판단을 건너뛴다. 열쇠를 받아 한 행만 내주는 함수를 두면 판단하는 곳과 막는 곳이 하나가 된다.

## Reconsider when

- 휴지통이 쌓여 저장 용량이 문제가 될 때. 자동 비우기를 두더라도 기간을 사용자에게 먼저 알리고 고르게 하는 쪽을 본다.
- 오프라인 편집 요구가 생길 때. 그때는 충돌 처리의 전제(내가 불러온 뒤 다른 기기가 바꿨는가)부터 다시 본다.

## Still-rejected alternatives

- 마지막 저장이 이기게 두기 — 구현이 가장 단순하지만 한 사람이 두 기기를 쓰는 흔한 상황에서 내용이 사라진다.
- 삭제 확인 창만 두고 즉시 지우기 — 휴지통보다 단순하지만, 폴더를 잘못 지웠을 때 되돌릴 방법이 없다.
- 소유자 조건을 애플리케이션 쿼리에만 두기 — 빠르지만 한 경로만 빠뜨려도 남의 노트가 새어 나간다.
